\chapter{Validación y resultados}

\section{Estrategia de validación}

La validación de Nuvlo combina pruebas automatizadas, revisión manual de la interfaz y comprobación con datos reales de Jira. Esta estrategia busca cubrir dos aspectos distintos: que los cálculos internos sean correctos y que la aplicación sea usable en los flujos principales.

Para conectar implementación y requisitos se utiliza una matriz requisito-prueba. En ella, cada requisito funcional, no funcional o de integración se asocia con una prueba, una revisión manual o una evidencia de uso. La matriz completa se recoge en la Tabla~\ref{tab:matriz-requisito-prueba}, dentro del capítulo de requisitos, y se resume en este capítulo desde el punto de vista de la validación.

\section{Tipos de prueba utilizados}

Antes de interpretar la matriz requisito-prueba conviene distinguir los tipos de comprobación empleados durante el desarrollo:

\begin{itemize}
    \item \textbf{Pruebas unitarias}: verifican funciones aisladas, especialmente cálculos de métricas, percentiles, validaciones de datos y reglas de alerta. Se ejecutan con Vitest~\cite{VitestGuide}.
    \item \textbf{Pruebas de integración}: comprueban que varias piezas funcionan juntas, por ejemplo API, repositorios, PostgreSQL, Redis y servicios de sincronización.
    \item \textbf{Pruebas con Jira real}: validan el flujo OAuth, la lectura de proyectos, la sincronización de incidencias y el almacenamiento local de datos procedentes de Jira Cloud.
    \item \textbf{Pruebas con \textit{dataset} \textit{offline}}: usan datos controlados para comprobar cálculos que requieren histórico suficiente, como \textit{Lead Time}, \textit{Cycle Time}, percentiles o \textit{Velocity}.
    \item \textbf{Pruebas end-to-end}: recorren la aplicación desde el navegador, incluyendo navegación, filtros, \textit{widgets}, alertas, \textit{logs} y modo demo. Se plantean con Playwright~\cite{PlaywrightDocs}.
    \item \textbf{Revisión visual y \textit{responsive}}: comprueba capturas en escritorio y móvil para validar legibilidad, navegación y coherencia con las vistas previstas.
\end{itemize}

\section{Pruebas automatizadas}

Las pruebas unitarias se centran en cálculos de métricas, percentiles, validaciones y reglas de alerta. Para ello se utiliza Vitest~\cite{VitestGuide}. Las pruebas de integración comprueban el comportamiento de la API, la persistencia y los servicios que dependen de PostgreSQL o Redis. En los casos relacionados con Jira se utilizan datos controlados o respuestas simuladas para evitar depender siempre de una conexión externa.

En el repositorio, estas comprobaciones se ejecutan mediante el comando \texttt{npm test}, que lanza las pruebas definidas en los paquetes del \textit{monorepo}. Además, se utiliza \texttt{npm run build} para comprobar que la aplicación puede compilarse correctamente y \texttt{npm run test:e2e} para ejecutar las pruebas de extremo a extremo disponibles.

Las pruebas end-to-end se plantean con Playwright~\cite{PlaywrightDocs}. Su objetivo es recorrer los flujos principales desde el punto de vista del usuario: entrada en modo demo, navegación por vistas, uso de filtros, sincronización, consulta de alertas y revisión del registro de actividad.

\section{Validación con Jira real}

La aplicación se ha probado con un proyecto real de Jira creado para demostración. Este escenario permite validar el flujo OAuth, la obtención de proyectos accesibles, la sincronización de incidencias y la persistencia en la base de datos local. Las capturas del manual de usuario muestran la aplicación funcionando con datos procedentes de Jira.

La validación con Jira real también sirve para detectar limitaciones prácticas. Por ejemplo, si las incidencias se crean y cierran en un intervalo muy corto, \textit{Lead Time} y \textit{Cycle Time} pueden aparecer como cero o valores poco representativos. Esto no implica que el cálculo esté ausente, sino que el histórico disponible no contiene todavía información temporal suficiente para un análisis realista.

\section{Validación con demo \textit{offline}}

La demo \textit{offline} cubre el caso contrario: proporciona datos preparados para que todas las métricas tengan valores visibles y coherentes. Este modo es útil para presentaciones, pruebas sin conexión y comprobaciones de regresión visual. Al no depender de la API de Jira, permite demostrar el comportamiento esperado de la interfaz incluso si la autenticación externa falla o no hay red disponible.


\section{Retos y problemas encontrados}

Durante el desarrollo se detectaron varios problemas que condicionaron decisiones técnicas y ayudaron a validar el comportamiento real de la aplicación. No todos fueron errores de programación en sentido estricto; algunos estuvieron relacionados con restricciones de las APIs externas, configuración del entorno o calidad de los datos disponibles.

\begin{itemize}
    \item \textbf{Autenticación con Atlassian}: el paso desde una prueba con token personal a OAuth 2.0 3LO obligó a rediseñar el flujo de acceso. Fue necesario configurar correctamente \textit{scopes}, URI de redirección, parámetro \textit{state}, PKCE y protección CSRF para que el usuario no tuviera que registrarse localmente.
    \item \textbf{Cambios en la API de Jira Cloud}: algunos endpoints de búsqueda utilizados en pruebas iniciales devolvían errores por cambios o deprecaciones. La sincronización se adaptó al endpoint actual con paginación y selección explícita de campos.
    \item \textbf{Calidad del histórico de Jira}: en proyectos recién creados, las incidencias no siempre tienen transiciones suficientes para calcular tiempos de flujo representativos. Por ello se incorporó una demo \textit{offline} con datos controlados que permite validar métricas aunque Jira real no tenga todavía histórico útil.
    \item \textbf{Gestión de sesión y expiración}: los \textit{tokens} de Atlassian pueden expirar o renovarse mediante \textit{refresh tokens} rotatorios. La aplicación separa la sesión del navegador de la autorización Atlassian y contempla renovación, cierre de sesión y errores de autenticación.
    \item \textbf{Persistencia y retención}: fue necesario distinguir datos persistentes, datos operativos y datos efímeros. PostgreSQL conserva la información necesaria para análisis e histórico, mientras que Redis almacena estados temporales con TTL.
    \item \textbf{Coherencia visual y \textit{responsive}}: algunas vistas y figuras iniciales resultaban demasiado grandes o se salían de márgenes. La interfaz y las capturas se revisaron para mejorar legibilidad en escritorio y móvil.
\end{itemize}

Estos retos permitieron ajustar el alcance de la versión implementada y separar con mayor claridad qué funcionalidades forman parte del producto mínimo viable y cuáles quedan como evolución futura.


\section{Resultados obtenidos}

El resultado actual es un producto mínimo viable (MVP) funcional de Nuvlo. La aplicación permite iniciar sesión con Atlassian, sincronizar información de Jira, consultar métricas ágiles, aplicar filtros, configurar \textit{widgets}, crear alertas y revisar actividad. Además, dispone de una demo \textit{offline} que actúa como respaldo para validación y presentación. Según la matriz requisito-prueba, no quedan requisitos \textit{Must Have} pendientes; los elementos parciales o futuros corresponden a mejoras clasificadas con menor prioridad.

El sistema todavía no pretende cubrir todos los escenarios de una herramienta comercial. Algunas mejoras, como métricas avanzadas, despliegue productivo, integración con repositorios de código o análisis predictivo, quedan fuera del alcance principal y se recogen como líneas de trabajo futuro.
