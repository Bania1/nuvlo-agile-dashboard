\chapter{Planificación}
\label{planificacionTemporal}

Este capítulo recoge la planificación temporal del proyecto. La distribución parte de la propuesta inicial, que estimaba una dedicación total de 300 horas, y se adapta a la evolución real del desarrollo: la integración principal se centra en \textit{Jira Cloud}, la autenticación se realiza mediante \textit{Atlassian OAuth} 2.0 3LO y se incorpora una demo \textit{offline} para validación y presentación.

La planificación se plantea de forma incremental. Cada bloque produce un resultado verificable, de modo que el sistema pueda probarse progresivamente en lugar de concentrar la validación al final. Esta forma de trabajo encaja con el propio objetivo del sistema: construir, medir, revisar y ajustar.

La abreviatura \textit{E2E} hace referencia a pruebas \textit{End-to-End}, es decir, pruebas de extremo a extremo que validan un flujo completo desde la interfaz hasta el comportamiento observable por el usuario.

\section{Criterios de planificación}

Para organizar el trabajo se han seguido los siguientes criterios:

\begin{itemize}
    \item Priorizar primero el análisis del problema, los objetivos y los antecedentes para evitar desarrollar una solución sin justificar su necesidad.
    \item Construir una base técnica mínima antes de implementar funcionalidades avanzadas: repositorio, entorno, base de datos, \textit{API} y cliente web.
    \item Resolver pronto la autenticación con \textit{Atlassian}, ya que condiciona la integración con \textit{Jira Cloud} y el acceso a datos reales.
    \item Separar la sincronización de datos del cálculo de métricas, permitiendo que la aplicación consulte \textit{PostgreSQL} en lugar de depender continuamente de la \textit{API} externa.
    \item Mantener una demo \textit{offline} con datos controlados para poder validar métricas y capturas aunque \textit{Jira} no esté disponible.
    \item Documentar y probar de forma continua, evitando que la memoria, el manual de usuario y el manual técnico queden como tareas aisladas al final.
\end{itemize}


\section{Enfoque iterativo de desarrollo}

Aunque la planificación se resume mediante fases y bloques de esfuerzo, el desarrollo no se ha organizado como una secuencia rígida de tareas independientes. En lugar de representar el trabajo mediante un diagrama de Gantt, se ha seguido un enfoque iterativo basado en ciclos aproximados de dos semanas. Esta decisión resulta más adecuada para un proyecto en el que análisis, implementación, pruebas y documentación han evolucionado de forma conjunta.

En cada ciclo se revisaba el estado de la aplicación, se priorizaba una parte funcional, se implementaba una mejora verificable y se actualizaba la documentación asociada. De esta forma, la planificación temporal no depende únicamente de fechas cerradas, sino de incrementos funcionales que pueden probarse y justificar su trazabilidad. \section{Ajustes respecto a la propuesta inicial}

La propuesta inicial planteaba una planificación amplia que incluía autenticación local, roles, integración con \textit{Jira} y \textit{GitHub}, reportes automáticos y validación con varios equipos. Durante el desarrollo, el alcance se ha ajustado para priorizar una versión completa, coherente y verificable alrededor de \textit{Jira Cloud} como fuente principal.

Los principales ajustes son los siguientes:

\begin{itemize}
    \item La autenticación local con registro de usuario se sustituye por \textit{Atlassian OAuth}, ya que el requisito real es que el usuario conecte su cuenta de \textit{Jira}.
    \item La integración con \textit{GitHub} se deja como ampliación futura para no mezclar métricas ágiles de \textit{Jira} con métricas de entrega software antes de completar el núcleo del sistema.
    \item Los reportes automáticos se posponen y se priorizan \textit{dashboard}, filtros, alertas, \textit{logs} e historial de actividad.
    \item La validación con usuarios externos se complementa con pruebas automatizadas, proyecto \textit{Jira} real de demostración y \textit{dataset} \textit{offline} controlado.
    \item La documentación se mantiene como actividad transversal, actualizando memoria y anexos conforme se consolidan decisiones de diseño e implementación.
\end{itemize}

Estos ajustes permiten mantener el límite de esfuerzo previsto y concentrar la validación en funcionalidades que pueden demostrarse de forma estable: autenticación con \textit{Atlassian}, sincronización desde \textit{Jira}, persistencia local, cálculo de métricas, visualización, alertas, actividad y demo \textit{offline}.
