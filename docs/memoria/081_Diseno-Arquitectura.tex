\chapter{Diseño y arquitectura del sistema}


\section{Enfoque general}

Nuvlo se ha diseñado como una aplicación web de apoyo al análisis de equipos ágiles que trabajan con Jira Cloud. La decisión principal de arquitectura ha sido separar claramente la interfaz, la API, la persistencia y los servicios de integración, manteniendo todo dentro de un \textit{monorepo} sencillo gestionado con \textit{npm workspaces}~\cite{NpmWorkspaces}. Esta organización permite que \textit{frontend}, \textit{backend}, esquema de base de datos, documentación y pruebas evolucionen en el mismo repositorio, lo que facilita la trazabilidad del desarrollo y la revisión de cambios.

El diseño se ha orientado a tres objetivos: aislar la dependencia con Jira Cloud, conservar una copia local suficiente para calcular métricas y ofrecer una interfaz comprensible para usuarios que no necesariamente conocen los detalles técnicos de la API. Por ello, el sistema no consulta Jira cada vez que el usuario abre una vista, sino que sincroniza datos, los normaliza y calcula las métricas sobre información persistida.

Se descartó dividir el sistema en varios repositorios porque habría aumentado el coste de configuración y coordinación. También se evitó mezclar \textit{frontend} y \textit{backend} en un único directorio sin separación interna, ya que habría dificultado explicar las responsabilidades de cada parte y mantener una estructura limpia durante la implementación.

\section{Arquitectura lógica}

La arquitectura sigue un esquema cliente-servidor. La aplicación web se ejecuta en el navegador y se comunica con una API propia. La API es la única parte del sistema que interactúa con Jira Cloud, PostgreSQL y Redis. De este modo, el \textit{frontend} no necesita conocer credenciales ni detalles internos de sincronización.

El \textit{frontend} se ha implementado con React y Vite~\cite{ReactDocs,ViteDocs}. La API se ha construido con Node.js y Express~\cite{NodeDocs,ExpressDocs}. La persistencia principal se realiza con PostgreSQL, accedida mediante Prisma~\cite{PostgreSQLDocs,PrismaDocs}. Redis se utiliza como almacenamiento temporal para datos de sesión, estados de seguridad del flujo OAuth y elementos de corta duración~\cite{RedisDocs}. El entorno local se levanta mediante Docker Compose~\cite{DockerComposeDocs}.

La organización lógica se puede leer por capas. La capa de presentación contiene las vistas y componentes visuales; la capa de aplicación expone la API y coordina los casos de uso; la capa de dominio concentra sincronización, cálculo de métricas y alertas; y la capa de persistencia encapsula el acceso a PostgreSQL y Redis. Esta separación reduce acoplamiento, facilita las pruebas y permite que los cambios en la interfaz no obliguen a modificar la integración con Jira.

Los diagramas incluidos en la memoria representan esta separación por capas y ayudan a entender el recorrido de los datos: el usuario entra por la interfaz, la API valida la sesión, sincroniza información desde Jira cuando procede y consulta la base de datos local para construir las métricas visibles en el \textit{dashboard}.

Según la especificación oficial de UML de OMG, un componente encapsula una parte sustituible del sistema y expone o requiere interfaces para colaborar con otros elementos~\cite{OMGUML251}. En este trabajo se utiliza esta notación para mostrar una vista lógica de la arquitectura, independiente de decisiones concretas de despliegue.

    \caption{Diagrama de componentes y arquitectura lógica del sistema}
    \label{fig:componentes-arquitectura-sistema}
\end{figure}

La Figura~\ref{fig:componentes-arquitectura-sistema} organiza el sistema en cuatro bloques principales: cliente web, servidor de aplicación, servicios externos y persistencia. Las flechas discontinuas representan dependencias entre componentes, es decir, relaciones de uso necesarias para completar las funcionalidades previstas.

\begin{itemize}
    \item \textbf{Cliente web}: agrupa la \texttt{Interfaz web}, el \texttt{Dashboard y vistas} y los componentes de \texttt{Filtros y configuración}. Este bloque permite al usuario autenticado consultar métricas, modificar criterios de análisis y acceder a las vistas principales del sistema.
    \item \textbf{Servidor de aplicación}: contiene la \texttt{API REST}, que centraliza las peticiones del cliente, y los componentes internos encargados del control de sesión, la sincronización con Jira, el cálculo de métricas y la gestión de alertas y \textit{logs}.
    \item \textbf{Servicios externos}: representan las dependencias con Atlassian. \texttt{Atlassian OAuth} se utiliza para la autenticación del usuario y \texttt{Jira Cloud API} proporciona los datos de proyectos, tableros, \textit{sprints} e incidencias.
    \item \textbf{Persistencia}: incluye los \texttt{Repositorios}, que aíslan el acceso a datos, y la \texttt{Base de datos del sistema}, donde se almacenan datos sincronizados, configuraciones, métricas calculadas, alertas y \textit{logs}.
\end{itemize}

Las relaciones principales muestran que el usuario accede al cliente web, el cliente consume la \texttt{API REST} mediante peticiones HTTP y el \textit{backend} coordina las operaciones internas. El \texttt{Control de sesión} depende de \texttt{Atlassian OAuth}; la \texttt{Sincronización Jira} consulta \texttt{Jira Cloud API}; el \texttt{Cálculo de métricas} trabaja sobre los datos sincronizados; y el componente de \texttt{Alertas y logs} registra eventos y evalúa umbrales a partir de las métricas disponibles. Finalmente, los repositorios concentran la lectura y escritura sobre la base de datos para mantener separada la lógica de negocio del almacenamiento.

\section{Modelo de datos y sincronización}

Se almacenan proyectos, tableros, incidencias, \textit{sprints}, estados, métricas calculadas, alertas y eventos de actividad. Esta decisión evita que cada interacción de la interfaz dependa de una llamada directa a Jira Cloud y permite recalcular métricas de forma controlada.

El modelo toma como base las entidades de análisis descritas en el capítulo anterior. La sincronización se realiza por ámbitos concretos, no como una descarga completa indiscriminada. El usuario selecciona el contexto de análisis y el \textit{backend} recupera los recursos asociados. Después normaliza los datos, actualiza PostgreSQL, registra el resultado de la operación y recalcula las métricas afectadas. Redis queda reservado para información efímera, como estados OAuth, protección CSRF, PKCE y cachés de vida corta.

El sistema solicita únicamente los campos necesarios y trabaja con paginación de la API de Jira~\cite{AtlassianJiraRestV3,AtlassianJiraIssuesApi}. Esta aproximación reduce el número de llamadas externas, evita recalcular información estable de forma innecesaria y encaja mejor con las restricciones de uso de una API remota.

\section{Seguridad}

El acceso final a Nuvlo se basa en OAuth 2.0 de Atlassian, concretamente en el flujo 3LO~\cite{AtlassianOAuth3LO}. El usuario no crea una cuenta local con contraseña: autoriza la aplicación con su cuenta de Atlassian y Nuvlo crea o actualiza la sesión asociada a ese usuario.

Para proteger el proceso de autenticación se han incorporado medidas habituales en aplicaciones web modernas: parámetro \textit{state}, PKCE y protección CSRF~\cite{OWASPOAuth2,OWASPCSRF}. Los \textit{tokens} no se exponen al navegador como credenciales persistentes de larga duración. La API actúa como capa intermedia y aplica validaciones antes de permitir operaciones protegidas.


\section{Diseño de interfaz}

El diseño de interfaz parte de los prototipos elaborados durante la fase de análisis y de las vistas incluidas en esta memoria. La interfaz final no replica cada prototipo de forma literal, pero conserva su planteamiento funcional: navegación lateral, \textit{dashboard} principal, vista de tablero, alertas, actividad y configuración.

La pantalla se organiza en zonas estables para reducir carga cognitiva. La zona lateral izquierda concentra la navegación principal y el proyecto activo; la zona superior muestra contexto, filtros y acciones frecuentes; y el área central se reserva para métricas, gráficos, listados o formularios según la vista seleccionada. Esta distribución permite que el usuario mantenga siempre una referencia clara de dónde está y qué datos está consultando.

En el \textit{dashboard}, las métricas principales se presentan como tarjetas resumidas. Los gráficos ocupan una zona de lectura más amplia y los avisos aparecen como elementos secundarios, sin competir con los indicadores principales. Las alertas se refuerzan con un contador visual y notificaciones ligeras, mientras que el registro de actividad queda separado para no mezclar análisis de métricas con trazabilidad técnica.

La estética de Nuvlo se apoya en una identidad propia basada en la idea de ``nube + flujo''. Se eligieron tonos verdes suaves, tarjetas claras, bordes redondeados y sombras discretas para diferenciar la aplicación de interfaces más genéricas. Para el \textit{dashboard} se tomó como inspiración visual una plantilla pública de administración moderna de Morphin~\cite{MorphinDashboardInspiration}, sin reutilizar su código fuente. La referencia se usó únicamente para orientar decisiones de composición, jerarquía visual, densidad de tarjetas y navegación.

\section{Prototipo de vistas de la aplicación}

El prototipo de vistas recoge una aproximación visual inicial de la interfaz del sistema. Su objetivo no es cerrar el diseño gráfico definitivo, sino comprobar que las funcionalidades principales descritas en los casos de uso tienen una representación coherente en pantalla: consulta de métricas, revisión del tablero, autenticación, trazabilidad de actividad, gestión de alertas y configuración de la cuenta.


Antes de llegar a las vistas finales se plantearon varios bocetos durante la fase de análisis. La base funcional de esos bocetos se definió primero mediante diagramas realizados en draw.io, donde se concretaron las vistas previstas, la navegación principal y los elementos que debía contener cada pantalla. A partir de esa estructura, se utilizó Stitch, herramienta de prototipado asistida por inteligencia artificial de Google~\cite{GoogleStitch}, para dar una apariencia más visual a algunas de esas ideas y comprobar cómo podían comportarse en una interfaz más cercana al producto final. Las propuestas obtenidas no se incorporaron como código fuente, sino como material de apoyo visual para tomar decisiones de diseño.

Las láminas generadas con Stitch muestran una interpretación visual de los bocetos funcionales previos y algunas ideas que evolucionaron durante el análisis y la implementación. En las primeras propuestas se contemplaban pantallas clásicas de inicio de sesión y registro, así como opciones de perfil y rol dentro de la propia aplicación. Finalmente, esa aproximación se simplificó para cumplir mejor el requisito de autenticación exclusiva mediante Atlassian: Nuvlo no gestiona usuarios locales ni contraseñas propias, sino que delega el acceso en OAuth con Jira/Atlassian. Por el mismo motivo, la configuración final se centra más en criterios de análisis, estados, filtros, alertas y sesión conectada que en una administración interna de roles.

Esta diferencia entre prototipo y versión final no se considera una desviación, sino una decisión de diseño derivada de las restricciones de seguridad y del alcance funcional. Los prototipos sirvieron para explorar navegación, distribución visual y jerarquía de información; la versión implementada conserva esa organización general, pero elimina elementos que podían duplicar responsabilidades ya cubiertas por Atlassian o aumentar innecesariamente la complejidad del sistema.
