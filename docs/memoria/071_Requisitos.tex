\chapter{Requisitos}

\section{Introducción}

En este capítulo se definen los requisitos que debe cumplir el sistema propuesto, estableciendo las funcionalidades principales, las restricciones técnicas y los datos necesarios para su funcionamiento. Esta especificación sirve como base para el diseño, la implementación y la posterior validación del sistema.

Para su elaboración se toma como referencia la práctica recomendada IEEE Std 830-1998, que propone que una especificación de requisitos software sea correcta, no ambigua, completa, consistente, verificable, modificable y trazable~\cite{IEEE8301998}. En este trabajo se adopta dicha referencia como guía para estructurar los requisitos y facilitar su posterior comprobación. La columna de verificación incluida en las tablas de requisitos indica el criterio o procedimiento previsto para comprobar cada requisito; la evidencia realmente obtenida durante el desarrollo se recoge posteriormente en la matriz requisito-prueba.

Asimismo, los requisitos se priorizan mediante la técnica MoSCoW, que clasifica cada requisito como \textit{Must Have}, \textit{Should Have}, \textit{Could Have} o \textit{Won't Have}. Esta técnica permite distinguir los requisitos imprescindibles para una versión funcional del sistema de aquellos que aportan valor, pero pueden planificarse como ampliaciones o mejoras~\cite{AgileBusinessConsortiumMoSCoW}.

\section{Descripción general del sistema}

El sistema consiste en una aplicación web orientada a la visualización de métricas ágiles para equipos que trabajan con marcos como \textit{Scrum} y \textit{Kanban}. Su objetivo principal es integrarse con \textit{Jira Cloud}, obtener información de proyectos e incidencias, procesarla y mostrarla mediante un \textit{dashboard} que facilite el análisis del flujo de trabajo, la evolución del equipo y determinados indicadores relacionados con la entrega de software.

La aplicación no pretende sustituir a \textit{Jira} como herramienta de gestión del trabajo, sino proporcionar una capa complementaria de análisis centrada en métricas ágiles. De esta forma, los usuarios pueden consultar información agregada, aplicar filtros, revisar alertas y detectar posibles desviaciones en el comportamiento del equipo o del flujo de trabajo.

\section{Actores del sistema}

Se identifica como actor principal al \textbf{Usuario}, entendido como la persona que utiliza \textit{Nuvlo} para autenticarse mediante \textit{Atlassian}, seleccionar un ámbito de análisis, sincronizar datos, consultar métricas, revisar alertas y acceder al registro de actividad.

Además, existen sistemas externos que participan en algunos casos de uso como actores secundarios: \textit{Atlassian} interviene en la autenticación \textit{OAuth} y \textit{Jira Cloud} \textit{API} proporciona los datos de proyectos, tableros, \textit{Sprints}, incidencias, estados, fechas, estimaciones y transiciones. Estos actores secundarios se indican en la descripción detallada de los casos de uso cuando corresponde, pero no se representan como iniciadores en el diagrama principal.

\section{Restricciones, supuestos y dependencias}

El sistema depende de la disponibilidad de \textit{Jira Cloud} y de su \textit{API} oficial para obtener los datos necesarios. Por tanto, cualquier limitación, cambio o indisponibilidad de dicha \textit{API} puede afectar al funcionamiento de la aplicación.

Se asume que los proyectos analizados contienen información suficiente y correctamente mantenida para calcular las métricas previstas. Por ejemplo, fechas de creación y resolución, historial de cambios de estado, estimaciones, asignaciones, \textit{Sprints} o campos equivalentes según la configuración del proyecto.

También se considera que la autenticación se realizará mediante los mecanismos oficiales de \textit{Atlassian}, evitando el registro local de usuarios y el uso de credenciales propias ajenas a \textit{Jira}. Durante el desarrollo pueden emplearse configuraciones locales de prueba, pero el objetivo del sistema final es apoyarse en un flujo de autenticación adecuado para un entorno real.

\section{Priorización de requisitos}

La priorización de requisitos se realiza mediante la técnica MoSCoW. En este trabajo se interpreta cada categoría de la siguiente forma:

\begin{itemize}
    \item \textbf{Must Have}: requisito imprescindible para que el sistema cumpla su propósito principal. En conjunto, estos requisitos constituyen el producto mínimo viable, o \textit{MVP}, de \textit{Nuvlo}.
    \item \textbf{Should Have}: requisito importante, pero no estrictamente necesario para una primera versión funcional.
    \item \textbf{Could Have}: mejora deseable que aporta valor, pero que puede posponerse sin comprometer el objetivo central del sistema.
    \item \textbf{Won't Have}: requisito descartado para el alcance actual del proyecto, aunque podría considerarse en trabajos futuros.
\end{itemize}

Los servicios externos \textit{Atlassian OAuth} y \textit{Jira Cloud} \textit{API} no se incluyen en este diagrama porque actúan como colaboradores secundarios dentro de determinados flujos, no como actores que soliciten funcionalidades al sistema.

Para facilitar su interpretación, se resumen a continuación los elementos principales del diagrama:

\begin{itemize}
    \item \textbf{Frontera del sistema}: el rectángulo delimita las funcionalidades que pertenecen al sistema de visualización de métricas ágiles.
    \item \textbf{Actor principal}: el usuario es quien inicia los casos de uso representados.
    \item \textbf{Casos de uso}: las elipses identifican funcionalidades observables desde la aplicación.
    \item \textbf{Inclusión}: la relación \textit{include} se utiliza cuando un caso de uso necesita ejecutar otro como parte de su comportamiento normal.
    \item \textbf{Extensión}: la relación \textit{extend} se utiliza cuando un caso de uso puede ampliar a otro de forma opcional o condicionada.
    \item \textbf{Precondiciones}: las restricciones de sesión se indican mediante una nota para evitar representar al usuario autenticado como una especialización artificial del usuario.
\end{itemize}

El diagrama utiliza un único actor primario:

\begin{itemize}
    \item \textbf{Usuario}: persona que inicia la interacción con \textit{Nuvlo}. Antes de autenticarse solo puede comenzar el acceso mediante \textit{Atlassian}; una vez autenticado puede seleccionar el ámbito de análisis, actualizar datos, consultar \textit{dashboards}, analizar métricas, configurar reglas de alerta, consultar alertas y revisar \textit{logs}.
\end{itemize}

No se utiliza una generalización entre \textit{Usuario} y \textit{Usuario autenticado}, ya que la autenticación representa un cambio de estado dentro del flujo de uso y no una especialización estable de actor. Tampoco se modela una herencia entre \textit{Atlassian} y \textit{Jira}, porque en este diagrama no solicitan funcionalidades al sistema, sino que participan como sistemas externos en casos concretos.

Las asociaciones del diagrama indican qué funcionalidades puede iniciar el usuario desde la aplicación. Además, se han añadido relaciones \textit{include} para hacer visibles dependencias funcionales obligatorias: CU-03 incluye CU-02, CU-05 incluye CU-02 y CU-06, CU-06 incluye CU-02 y CU-03, y CU-08 incluye CU-07. También se representan dos relaciones \textit{extend}: CU-09 puede extender CU-03 cuando el usuario revisa los \textit{logs} asociados a una actualización, y CU-08 puede extender CU-05 cuando el usuario accede a las alertas desde el contexto del \textit{dashboard}. La autenticación se representa como precondición común de los casos CU-02 a CU-09 mediante una nota, porque no implica ejecutar el inicio de sesión en cada interacción, sino disponer de una sesión \textit{Atlassian} válida.
